# 🧩 工程规约：AI Coding 的任务分解与上下文管理

**目标：** 在大语言模型上下文窗口有限的前提下，用确定性的边界与自包含任务设计，稳定完成复杂开发工作，并支持多会话/多 worktree 并行。

---

## 1. 问题定义（硬约束）

### 1.1 LLM 的上下文约束

- **上下文窗口有限**：即便长上下文模型，也不足以一次性装下中型代码库 + 需求 + 历史讨论。
- **注意力衰减（lost in the middle）**：位于上下文中部的信息更容易被忽略。
- **推理时间线性增长**：复杂任务的推理步骤越多，串行执行延迟越高；并行可显著缩短总耗时。

### 1.2 “事后补救”方案的局限

- **截断历史**：丢失早期关键信息。
- **摘要压缩**：细节损失与信息失真。
- **RAG 按需检索**：检索质量不稳定，且执行期外部查询会扩大不确定性。

**结论：** 更有效的策略是在**任务设计阶段**就控制上下文边界，而不是执行时再补救。

---

## 2. 核心原则：Self-Contained（自包含）

### 2.1 定义

**Self-Contained（自包含）**：每个执行单元（Story/Task/Session/Subagent）应拥有完成任务所需的全部信息，且不依赖执行时的外部查询。

### 2.2 为什么在 AI Coding 中特别重要

人类开发者可以随时查文档、问同事、在脑中维持全局视图；AI Agent 的“工作记忆”就是上下文窗口，窗口外信息等同不存在。

**因此：任务边界设计直接决定任务是否能完成。**

### 2.3 Self-Contained 的三个层次

- **文档层（Spec/开发文档）**
  - 必须包含：需求、接口定义、约束条件、验收标准。
  - 目标：让实现阶段尽量不需要“再问一句”。
- **任务层（Story/Task）**
  - 可独立验收：不需要查询其他 story 的隐藏前置结论。
  - 依赖必须被显式声明为：契约 / mock / 顺序执行。
- **执行层（Session/Subagent）**
  - 上下文自足：执行中不临时“再去找信息”。
  - 输入材料应被组织为：目标 + 约束 + 现状 + 接口 + 验收。

## 3. 设计层：任务分解策略

### 3.1 目标

任务分解的目标是把大任务拆成多个小任务，使得：

- 每个小任务的上下文需求在 LLM 能力范围内
- 小任务之间依赖最小化
- 小任务结果可被聚合成整体结果

### 3.2 边界划分依据：确定性接口（Deterministic Interface）

有效边界应是**确定性的接口**，而不是模糊的“模块名”。

**确定性接口的特征：**

- **输入/输出明确定义**：类型、格式、约束
- **行为可验证**：可写测试用例或可执行检查
- **无隐式依赖**：不依赖全局状态或执行期外部查询

典型边界：API Contract（OpenAPI/TypeSpec）、Schema（zod/json schema）、文件产物列表（哪些文件必须改动/新增）。

### 3.3 两种主流分解方法

- **方法 A：Epic → Story → Task**
  - 适用：需求复杂、多人协作、需要追踪。
  - 要求：每个 story 在计划阶段消化跨 story 依赖，转化为明确契约。
- **方法 B：文档驱动的阶段分解**
  - Phase 1：需求分析（PRD/用户故事/验收）
  - Phase 2：架构设计（模块边界/API 契约/数据模型）
  - Phase 3：开发规划（分阶段执行文档）
  - Phase 4：并行开发（多 Session/多 worktree）
  - Phase 5：集成测试（E2E/回归）
  - 适用：大型项目，追求一次性高质量交付。

### 3.4 跨任务依赖（必须在设计阶段解决）

- **数据依赖**：B 需要 A 的输出
  - 处理：定义数据契约；A 先执行；B 只消费契约。
- **接口依赖**：A 调用 B 的 API
  - 处理：先定 API Contract；必要时用 mock server 或 stub 先行。
- **代码依赖**：共享工具函数
  - 处理：提前提取到公共库或公共模块。
- **知识依赖**：需要业务背景
  - 处理：在 Spec 中显式写明核心背景与约束，避免执行期补问。

## 4. 执行层：Orchestrator–Worker 协作协议

### 4.1 角色划分

- **Orchestrator（编排器）**
  - 只负责：分解、依赖分析、调度、结果聚合、异常处理。
  - 不负责：具体编码实现与细节推导。
- **Worker（工作者）**
  - 单一职责、无状态：每次执行不假设持久记忆。
  - 产出应可独立验收：按契约产出代码/测试/文档更新。

### 4.2 上下文隔离与结果摘要（强制）

- **Session 隔离**：每个 Worker 使用独立会话，避免上下文污染。
- **结果过滤**：Orchestrator 只吸收 Worker 的关键结果（文件清单 + 摘要 + 风险 + 下一步）。
- **动态路由**：仅在必要时将 A 的输出传给 B。

**Worker 回传必须是“结果摘要”，禁止回传长过程。**

回传格式详见：`specs/zh/protocols/orchestrator-worker-output-format.md`。

## 5. 并行执行模式与边界

### 5.1 并行类型

- **真并行**：多个 Agent/进程同时执行（效率最高，基础设施要求高）。
- **伪并行**：一次发起多任务，串行执行（实现简单，效率提升有限）。
- **阶段并行**：同阶段并行、跨阶段串行（折中方案）。

### 5.2 MapReduce 思路

- **Map**：将任务拆为相互独立的子任务并行执行。
- **Reduce**：聚合结果，形成最终交付。

适用：信息收集、批量文件处理、多方案探索。

### 5.3 不适合并行的情况（禁止强行并行）

- 强依赖：B 输入必须来自 A 输出
- 共享状态：多个 Worker 需要读写同一资源
- 串行业务流程：业务逻辑本身线性

### 5.4 Git worktree 作为文件系统隔离

当多个 Worker 需要同时修改代码时，优先采用 worktree 隔离，避免互相覆盖与上下文污染。

---

## 6. 工程落地：质量门槛

- **任务设计门槛**：每个 Task 必须自包含（依赖、契约、验收完整），详见：`specs/zh/protocols/self-contained-task-template.md`。
- **开发门槛**：代码可运行、lint/类型检查通过、关键用例可验证。
- **集成门槛**：E2E/回归用例通过；问题修复后重新进入测试。
